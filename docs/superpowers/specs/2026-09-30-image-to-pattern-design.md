# 一起拼豆（WeeFuse）第一阶段：图片转图纸 设计规格

- 日期：2026-09-30
- 状态：待实现
- 范围：功能一「图片转图纸」。功能二（AI 生图纸）、功能三（拼豆社区）不在本规格内，仅在「后续阶段预留」一节说明接口关系。

---

## 1. 背景与目标

WeeFuse 是一款拼豆辅助 App，中文名「一起拼豆」，Android 优先（Tauri 2），MIT 开源。

**第一阶段目标**：把一张图片转成可照着拼的拼豆图纸，并导出成图片。

**首要用户**：设计者本人及其女儿（小学生），主要在 **Android 平板**上使用。这决定了 UI 必须大触控目标、大字号、少术语，且必须自适应平板宽屏。

**成功标准**：

1. 选图、选区、选尺寸、生成图纸，全流程离线可用（不依赖网络）。
2. 图纸上每格标注 MARD 色号（`A1` / `H1` / `B3` 形式），用户拿着色号能去拼豆店找豆。
3. 导出的施工图包含网格、格内色号、行列坐标、图例与用量表。
4. 生成结果可手动微调（单颗改色、框选批量改色），且可撤销。
5. 图纸可保存为本地工程，之后重新打开继续编辑或重新导出。

### 2.1 本阶段做

### 2.2 本阶段明确不做

| 不做 | 理由 |
|---|---|
| 抖动（Floyd–Steinberg） | 拼豆颗粒大，抖动噪点在实物上偏脏，社区图纸普遍不用。留接口位，不实现 |
| 自由形状抠图 / 自动去背景 | 需要图像分割模型，属 AI 能力，非第一版 |
| 后端、账号、云同步 | 功能一完全离线即可交付；后端等真实需求出现再建 |
| 专门的「儿童模式」 | 整体按大触控目标 + 少术语设计即可覆盖，多一套模式只增加维护面 |
| PDF / A4 分页打印 | 导出 PNG 分片已能满足施工，PDF 留待有明确需求 |
| 色卡在线更新 | 第一版色卡随版本内置，导入自定义色卡留待后续 |
| 多品牌色卡切换 | 只做 MARD 221，但数据结构支持多套（换品牌 = 换一份 JSON） |

## 3. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | Vue 3 + TypeScript + Vite + Pinia + Tailwind CSS v4 | 与 WeeCount 一致 |
| 客户端壳 | Tauri 2.0（Android 为正式目标，桌面端仅开发调试） | 与 WeeCount 一致 |
| 图像引擎 | **纯前端 TS，`src/core/` 零依赖纯函数** | 见 3.1 |
| 测试 | vitest（happy-dom） | 与 WeeCount 一致 |
| 后端 | **本阶段不建** | 空目录是负债，等功能二再加 |

### 3.1 为什么图像引擎放前端 TS 而不是 Rust

- **量级不构成性能问题**：200×200 豆 = 4 万格。直方图 + 聚类的复杂度与像素数解耦（见 4.4），代表色映射只有数千次距离计算。真正的耗时是 WebView 原生解码一张 1200 万像素照片，与算法放哪层无关。
- **迭代速度差一个数量级**：纯 TS 可在 `npm run dev` 的浏览器里直接调 UI 和算法，改一行热重载；Rust 每次改算法都要 `cargo build` + Android 交叉编译 + 装机。
- **功能二直接复用**：AI 生图纸的产物同样要喂进这条流水线，引擎在前端意味着 AI 功能零改动复用。
- **可测试性**：纯函数能被 vitest 直接覆盖，Rust 侧还需另维护一套测试。
- **反面**：若将来要做批量处理数百张图或 1000×1000 豆以上，才值得迁到 Rust。届时 `core/` 的纯数据进出接口是这个迁移的边界。

明确否决「混合方案」（预览走 TS、导出走 Rust）：同一算法两份实现，任何像素级偏差都会变成"预览与导出不一致"这类极难排查的 bug，收益为零。

### 3.2 渲染方式

预览与导出**统一用 Canvas 2D 自绘**。不用 DOM 铺格子（1 万个 div 会卡死），不用 SVG（4 万个 rect 同样低效）。点击某颗豆的命中检测由 canvas 坐标换算完成，不依赖 DOM 事件委托。

### 4.2 色卡模型

```ts
// core/palette/types.ts
interface PaletteColor { code: string; name: string; rgb: [number, number, number] }

interface Palette {
  id: string        // "mard221"
  name: string      // "MARD 221 色"
  source: string    // 数据来源
  accuracy: string  // 精度声明，会显示在 UI 与导出图上
  colors: PaletteColor[]
}
```

色卡是**数据文件**，不是代码常量。换品牌 = 换一份 JSON，量化算法只依赖 `Palette` 接口。

### 4.3 图纸模型

```ts
// core/pattern/types.ts
const EMPTY = 0xffff   // cells 中的空格标记：该格不拼豆

interface Pattern {
  width: number          // 豆数（列）
  height: number         // 豆数（行）
  paletteId: string
  cells: Uint16Array     // 行优先，长度 width*height；值为 colors 的下标，EMPTY 表示空格
}
```

- 用 `Uint16Array` 而非二维数组：4 万格仅 80KB，拷贝与序列化都便宜；`Uint16` 上限 65535 色，足够。
- **用量统计（每个色号多少颗）不存进 `Pattern`，永远由 `cells` 派生**。存下来的派生数据迟早与真相对不上，且此类 bug 极难定位。

### 4.4 工程文件格式

```jsonc
{
  "format": "weefuse-project",
  "version": 1,
  "id": "…",
  "name": "小猫",
  "createdAt": "2026-09-30T10:00:00Z",
  "updatedAt": "2026-09-30T10:20:00Z",
  "palette": { "id": "mard221", "codes": ["A1", "H1", "F2"] },
  "grid": [0, 0, 1, 2, 2, 1, 65535],     // 行优先，下标到 palette.codes；65535 = 空格
  "params": { "longSide": 58, "maxColors": 32, "crop": { "x": 0, "y": 0, "w": 800, "h": 800, "rotate": 0 } },
  "thumbnail": "data:image/webp;base64,…"
}
```

`crop` 的坐标一律基于**原图未旋转坐标系**，`rotate` 为顺时针 90° 的次数（0–3），应用顺序固定为「先旋转、后裁剪」。此约定必须写进 `crop.ts` 的文档注释，否则两处坐标系混用会产出难以察觉的错版图纸。

三个关键决策：

1. **落盘存色号字符串，不存色卡数组下标。** 若将来校准色值或重排色卡顺序，按下标存的旧工程会全部静默错位——图纸看起来正常，色号全错。存色号永远对得上。
2. **原图只存一张最长边 1600px 的缩略副本**（WebP，约 200–400KB），不存全尺寸原图。这样「对比预览」和「回头改裁剪框/色数档位重跑」都可用，工程文件也不会膨胀到数 MB。
3. `params` 必须落盘，否则打开旧工程无法回到原始参数重新生成。

## 5. 算法流水线

```
① 解码预览图 → ② 矩形选区 → ③ 裁剪 + 重采样到豆格
→ ④ 直方图 + median cut 压色到 N → ⑤ 代表色映射色号 → ⑥ 逐格映射
```

### ① 解码

**本流水线有两次独立的解码，尺寸不同、目的不同，不可混用：**

- **预览解码**（用于选区 UI）：位图长边不超过约 1600px，避免整图进内存。仅在选区页使用。
- **生成解码**（用于产出豆格）：宽度取 `长边豆数 × 4`，保证每格至少 4×4 像素参与面积平均。在选区确定后按选区坐标重新解码，与预览解码的分辨率无关。

原始图片的像素尺寸单独读取（只读头部即可），用于把选区 UI 上的坐标换算回原图坐标。

### ③ 裁剪 + 重采样

**关键实现点**：用 `createImageBitmap(blob, sx, sy, sw, sh, { resizeWidth })` 在**解码阶段直接裁出选区并缩放**，全图从不进内存。朴素做法（整图解码 → canvas 裁剪 → 缩放）在 4000×3000 照片上会产生约 48MB 位图，在 Android WebView 上是实打实的 OOM 风险，而用户可能只要拼一个 58×58 的小图。

目标解码宽度取 `长边豆数 × 4`，保证每格至少 4×4 像素参与平均。

**风险与降级**：`resizeWidth` 的重采样质量取决于 WebView 的 Skia 实现，若为最近邻，小图会出现噪点与摩尔纹。因此 `decode.ts` 暴露一个 **`Decoder` 接口，含两条实现**：

- 快路径：`createImageBitmap` 一次完成裁剪 + 缩放
- 保底路径：`createImageBitmap` 仅裁剪（取原生像素）→ 自行实现面积平均重采样

两条路径的输出都是 `ImageData`，下游无感。**实现第 3 步先做真机对比实验（高对比度棋盘格图）再决定默认路径，在此之前不假定快路径可用。**

### 重采样规则

- 每格 = 对应原图区域的**面积平均**（不是取中心像素；中心像素会带来明显噪点）
- 按 alpha 加权平均
- **整格全透明 → 标记为空格（`EMPTY`）**，不参与后续量化

### ④ 直方图 + median cut

- 先把像素 RGB 各压 5bit，归入 32768 个直方图桶
- 在**桶**上跑 median cut，切割轴取 Lab 空间中的最长轴，按中位数切
- 输出 N 个代表色（N = 16 / 32 / 不限）

先直方图的意义：把复杂度从"像素数"解耦为"桶数"，4 万像素与 400 万像素耗时相同。

### ⑤ 代表色 → 色号

**这是整条流水线的结构性优势**：逐格搜索需 4 万 × 221 ≈ 880 万次距离计算，而代表色只有 N ≤ 32 个，仅需 32 × 221 = **7000 次**。所以这里可以直接用最准的 **CIEDE2000**，不必为速度退让到 RGB 欧氏距离。

副作用是好的：多个代表色可能落到同一色号，实际用色比档位更少。UI 显示为「档位 32 色，实际用了 24 种」。

### ⑥ 逐格映射

每格均值色 → 最近的已选代表色 → 取其色号。预先把格子色与代表色都转成 Lab，暴力搜索即可（4 万格 × ≤32 代表色）。

### 抖动

不实现。`quantize/` 预留参数位与 `dither.ts` 的位置，将来加入不破坏结构。

## 6. 交互与 UI

### 6.1 流程

```
首页（图纸库）
 ├─ 新建 → 选图（相册 / 拍照）
 ├─ 系统分享进入 → 直接进选区
 └─ 打开已有工程 → 编辑器

选区页 → 设置页（长边豆数 / 色卡 / 用色档位）→ 编辑器 → 导出页
```

### 6.2 自适应布局

| 断点 | 布局 |
|---|---|
| < 768px（手机） | 单列向导，逐步推进 |
| ≥ 768px（平板） | 左右分栏：左侧大图预览，右侧参数与工具；改参数即时看到结果，无需来回翻页 |

### 6.3 平板上的三个技术点

1. **预览 Canvas 必须按 `devicePixelRatio` 缩放**（`canvas.width = cssWidth * dpr`，再 `ctx.scale(dpr, dpr)`），否则高分屏上预览发虚。导出图相反，按固定像素密度绘制，与 DPR 无关。
2. **触控命中**：一颗豆在屏幕上常只有几像素，手指点不准。编辑器默认放大到**每格 ≥ 24 CSS px**，小尺寸图自动放大铺满；支持双指捏合缩放与拖动平移；画笔支持拖动连续涂改一串格子。
3. **横屏编辑**：平板横屏 + 两栏是主要施工姿态。旋转时需重算 canvas 尺寸，工程状态不得丢失。

### 6.4 面向儿童的设计原则

不做独立「儿童模式」，整体按以下原则设计（对成人同样不减分）：

- 大触控目标、大字号
- 用词口语化：「用了几种颜色的豆子」而非「调色板量化数」
- 破坏性操作靠**可撤销**兜底，而不是弹窗拦截（弹窗小孩只会乱点）

### 6.5 编辑器

- 预览 Canvas：缩放、平移、网格线开关
- **色号调色板**：列出当前图纸用到的色号 + 每色颗数，点选即设为画笔颜色
- 工具：画笔（单颗 / 拖动连涂）、框选批量换色、吸管、撤销 / 重做
- **空格子可点**：在「空 ↔ 当前色」之间切换（抠图场景必需）
- 预览分层渲染：色块层缓存于离屏 canvas，单格改动只重绘该格；网格线 / 选中高亮画在叠加层

## 7. 导出

### 7.1 两个渲染器

- `sheet.ts` 施工图：网格线 + 格内色号 + 行列坐标刻度（每 5 或 10 格） + 底部图例与用量表（色块、色号、颜色名、颗数） + 顶部信息条（尺寸、色卡、总颗数、用色数、生成时间）
- `share.ts` 分享图：纯色块，无网格无文字

`layout.ts` 负责画布尺寸计算、字号自适应与分片决策，两个渲染器共用。

### 7.2 字号自适应降级

格内色号仅当格子像素 ≥ 32px 时绘制；否则自动省略，并在界面上明确提示「图太大，已省略格内色号，建议分片导出」，而不是画一堆看不清的糊字。

### 7.3 Canvas 尺寸上限与分片

Android WebView 的 canvas 单边上限一般在 4096–16384px 之间，**需真机实测定值**。降级链：

1. 降低格子像素（下限 8px）
2. 仍超限 → 按拼豆板分区导出多张，每张标注列范围（如「第 1–29 列」）

分片是本功能最易出 bug 的地方（坐标偏移、接缝错行、图例重复），需重点测试。

### 7.4 保存到相册

Android 上写入系统相册需走 MediaStore，**属待验证路径**。降级方案：保存到 App 私有目录 + 调起系统分享面板（微信、相册均可接收），功能等价、用户多点一步。先探，探不通即用降级方案并在 UI 中说明，不假定其可用。

## 8. 错误处理与边界

| 场景 | 行为 |
|---|---|
| 图片解码失败（损坏文件、不支持的格式） | 明确提示具体原因，不静默失败 |
| 图片过大（长边 > 8000px） | 先只读尺寸，超阈值则提示并强制使用缩略图路径 |
| 选区过小（不足 1 颗豆） | 阻止进入下一步并提示 |
| 长边豆数越界 | 允许 1–500；超过 300 提示导出将分片 |
| 全透明图 / 生成结果全为空格 | 提示「这张图没有可拼的像素」，不产出空图纸 |
| 色卡 JSON 校验失败 | 启动即报错（内置数据不应失败，但仍校验 schema） |
| 工程文件损坏 / 版本不认识 | 提示并跳过该条，不使列表整体不可用 |
| 保存工程失败（磁盘满） | 提示，保留内存中的编辑态不丢 |
| 导出降级链全部失败 | 明确提示，并建议降低豆数 |
| 撤销栈内存上限 | 上限 50 步，超出丢弃最旧的记录 |
| 分享 / 保存相册失败 | 降级到系统分享面板 |

## 9. 测试策略

`core/` 全部为纯函数，vitest 覆盖：

| 对象 | 用例要点 |
|---|---|
| `color/space` | RGB↔Lab 往返精度 |
| `color/distance` | **CIEDE2000 使用 Sharma 等人的公开标准测试向量**（验证实现正确性，非自证） |
| `image/resample` | 合成图（纯色块 / 棋盘 / 渐变）断言面积平均结果；alpha 加权；全透明格 → 空格 |
| `quantize/medianCut` | 已知像素集合 → 断言代表色数量与覆盖性 |
| `quantize/nearest` | 8 色假色卡断言映射结果 |
| `pattern/build` | 4×4 合成图端到端断言 `cells` 色号 |
| `pattern/edit` + `history` | 改色结果、撤销 / 重做、栈上限 |
| `pattern/stats` | 用量统计（含空格不计入） |
| `render/layout` | 画布尺寸、字号降级阈值、分片边界（只算布局，不真实绘制） |
| `render/*` | happy-dom + mock CanvasRenderingContext2D，断言 fillRect / fillText 调用次数与关键坐标、颜色 |

## 11. 色卡数据

- **主色卡：MARD 221 色**。色号体系为 `A / B / C / D / E / F / G / H / M` 九大色系 + 序号，形如 `A1`、`B3`、`H1`。这是拼豆圈的事实标准，网络流传图纸的色号基本都是这一套。
- **数据来源**：第三方公开色号表（如 [豆豆工坊 MARD 色卡](https://www.doudougongfang.com/kb/beads/mard-palette)）。抓取后整理为 `core/palette/builtin/mard221.json`。
- **已知缺口**：M 系列仅取得 M1–M4，M5–M15 需换来源补齐，补不齐则在文件中如实标注为部分数据。
- **精度声明**：MARD 官方未公开色值，第三方整理值与实物豆存在偏差。此声明必须显示在色卡 UI 与导出图纸上（「屏幕色仅供参考，以实物为准」）。
- **可替换性**：色卡为独立 JSON 文件。若品牌方对数据有异议，删除或替换该文件即可，不涉及任何代码改动。

注：未采用开源项目 `carolineyang095-code/ycs-beads-converter` 的数据，因其为 AGPL 许可，会污染本项目的 MIT 授权。`liberatrrot/BeadPalette`（MIT）可作为算法思路参考，但其色卡仅为 16 色示例子集，不复用。

## 14. 实现顺序

1. **骨架**：`CLAUDE.md` / `AGENTS.md`、Tauri 2 + Vue 3 + Tailwind v4 + vitest 工程、`ci.yml`（lint + typecheck + test + `cargo check`）
2. **`core/color` + `core/palette` + MARD221 数据**（完全独立可测，不碰 UI）
3. **`core/image` 解码器对比实验**（定 R1 结论）
4. **`core/quantize` + `core/pattern`**
5. **向导页**：选图 → 选区 → 尺寸 / 档位 → 生成
6. **编辑器**：预览 + 画笔 / 框选 / 吸管 + 撤销重做
7. **导出**：施工图 / 分享图 / 分片降级 / 保存分享
8. **图纸库**：工程文件读写与列表
9. **平板自适应联调 + 真机清单**

第 2、3 步风险最低、价值最高：完全不依赖 UI，写完即可被测试证明正确，且功能二将来直接复用。

**本规格体量偏大，实现计划应拆成两份**，以第 5 步为界：

- **计划 A「引擎」**：第 1–4 步。交付物是一个被测试证明正确的纯 TS 引擎（含 R1 解码器结论）。此时还看不到界面。
- **计划 B「应用」**：第 5–9 步。交付物是能跑在平板上的完整 App。

先做 A 再做 B，好处是引擎的正确性在引入 UI 复杂度之前就已锁定——UI 阶段出现的偏差可以确定是 UI 层的问题，不必回头怀疑算法。
