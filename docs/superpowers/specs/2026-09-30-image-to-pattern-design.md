# 一起拼豆（WeeFuse）第一阶段：图片转图纸 设计规格

- 日期：2026-09-30
- 状态：待实现
- 范围：功能一「图片转图纸」。功能二（AI 生图纸）、功能三（拼豆社区）不在本规格内，仅在「后续阶段预留」一节说明接口关系。

---

## 1. 背景与目标

WeeFuse 是一款拼豆辅助 App，中文名「一起拼豆」，Android 优先（Tauri 2），MIT 开源。

**第一阶段目标**：把一张图片转成可照着拼的拼豆图纸，并导出成图片。

**首要用户**：设计者本人及其女儿（小学生），主要在 **Android 平板**上使用。这决定了 UI 必须大触控目标、大字号、少术语，且必须自适应平板宽屏。

**成功标准**：

1. 选图、选区、选尺寸、生成图纸，全流程离线可用（不依赖网络）。
2. 图纸上每格标注 MARD 色号（`A1` / `H1` / `B3` 形式），用户拿着色号能去拼豆店找豆。
3. 导出的施工图包含网格、格内色号、行列坐标、图例与用量表。
4. 生成结果可手动微调（单颗改色、框选批量改色），且可撤销。
5. 图纸可保存为本地工程，之后重新打开继续编辑或重新导出。

| 不做 | 理由 |

## 3. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | Vue 3 + TypeScript + Vite + Pinia + Tailwind CSS v4 | 与 WeeCount 一致 |
| 客户端壳 | Tauri 2.0（Android 为正式目标，桌面端仅开发调试） | 与 WeeCount 一致 |
| 图像引擎 | **纯前端 TS，`src/core/` 零依赖纯函数** | 见 3.1 |
| 测试 | vitest（happy-dom） | 与 WeeCount 一致 |
| 后端 | **本阶段不建** | 空目录是负债，等功能二再加 |

### 3.1 为什么图像引擎放前端 TS 而不是 Rust

- **量级不构成性能问题**：200×200 豆 = 4 万格。直方图 + 聚类的复杂度与像素数解耦（见 4.4），代表色映射只有数千次距离计算。真正的耗时是 WebView 原生解码一张 1200 万像素照片，与算法放哪层无关。
- **迭代速度差一个数量级**：纯 TS 可在 `npm run dev` 的浏览器里直接调 UI 和算法，改一行热重载；Rust 每次改算法都要 `cargo build` + Android 交叉编译 + 装机。
- **功能二直接复用**：AI 生图纸的产物同样要喂进这条流水线，引擎在前端意味着 AI 功能零改动复用。
- **可测试性**：纯函数能被 vitest 直接覆盖，Rust 侧还需另维护一套测试。
- **反面**：若将来要做批量处理数百张图或 1000×1000 豆以上，才值得迁到 Rust。届时 `core/` 的纯数据进出接口是这个迁移的边界。

明确否决「混合方案」（预览走 TS、导出走 Rust）：同一算法两份实现，任何像素级偏差都会变成"预览与导出不一致"这类极难排查的 bug，收益为零。

### 3.2 渲染方式

预览与导出**统一用 Canvas 2D 自绘**。不用 DOM 铺格子（1 万个 div 会卡死），不用 SVG（4 万个 rect 同样低效）。点击某颗豆的命中检测由 canvas 坐标换算完成，不依赖 DOM 事件委托。

### 4.2 色卡模型

```ts
// core/palette/types.ts
interface PaletteColor { code: string; name: string; rgb: [number, number, number] }

interface Palette {
  id: string        // "mard221"
  name: string      // "MARD 221 色"
  source: string    // 数据来源
  accuracy: string  // 精度声明，会显示在 UI 与导出图上
  colors: PaletteColor[]
}
```

色卡是**数据文件**，不是代码常量。换品牌 = 换一份 JSON，量化算法只依赖 `Palette` 接口。

### 4.3 图纸模型

```ts
// core/pattern/types.ts
const EMPTY = 0xffff   // cells 中的空格标记：该格不拼豆

interface Pattern {
  width: number          // 豆数（列）
  height: number         // 豆数（行）
  paletteId: string
  cells: Uint16Array     // 行优先，长度 width*height；值为 colors 的下标，EMPTY 表示空格
}
```

- 用 `Uint16Array` 而非二维数组：4 万格仅 80KB，拷贝与序列化都便宜；`Uint16` 上限 65535 色，足够。
- **用量统计（每个色号多少颗）不存进 `Pattern`，永远由 `cells` 派生**。存下来的派生数据迟早与真相对不上，且此类 bug 极难定位。

### 4.4 工程文件格式

> **2026-10-03 修订**：本节原格式与「原图只存 1600px 缩略副本」那条决策由
> [计划 B1 规格](2026-10-03-app-skeleton-design.md) §4.3 修订，共三处——① 存全尺寸原图副本
> 并与「列表封面」解耦（原决策自相矛盾：1600px 缩略图重跑得到的是另一张图纸，而 `params`
> 落盘的唯一意义就是回到原始参数重新生成）② 列表封面改用 ≤512px 的**图纸**缩略图（列表要找的是
> 「那张小猫拼豆图」，不是「小猫照片」）③ 显式落盘 `width` / `height`（原格式下尺寸只有乘积
> 可得，`3×4` 与 `4×3` 字节完全相同，转置损坏无法被发现）。**下面的代码块已按修订后的口径更新。**

```jsonc
{
  "format": "weefuse-project",
  "version": 1,
  "width": 3,
  "height": 3,
  "palette": { "id": "mard221", "codes": ["A1", "H1", "F2"] },
  "grid": [0, 0, 1, 2, 2, 1, 65535],     // 行优先，长度 = width*height，下标到 palette.codes；65535 = 空格
  "params": { "longSide": 58, "maxColors": 32, "crop": { "x": 0, "y": 0, "w": 800, "h": 800, "rotate": 0 } }
}
```

**本 JSON 只承载「图纸本体」。** `id` / `name` / 时间戳 / `thumbnail` 不在其中——它们是列表展示数据，
属于工程记录的 `meta` 部分，与「一张图纸长什么样」是两件事（字段定义见 B1 规格 §4.4）。

`crop` 的坐标一律基于**原图未旋转坐标系**，`rotate` 为顺时针 90° 的次数（0–3）。**概念上的应用顺序是「先旋转、后裁剪」**。

实现上利用 90° 整数倍旋转的可交换性，把它等价地做成「按未旋转坐标裁剪 → 重采样到豆格 → **旋转网格**」（`services/pipeline.ts`）：旋转只作用在最终的 58×58 网格上，而不是原图尺寸的位图上，代价小一个数量级。**这个等价性只在 90° 整数倍下成立**——将来若引入任意角度旋转，等价性立刻失效，两处坐标系必须重新对齐，否则就会产出本节原本警告的那种「难以察觉的错版图纸」。

（本约定写在 `services/pipeline.ts` 的注释与本节；**不存在 `crop.ts`**。）

四个关键决策（第 2 条为 2026-10-03 修订，原文为「原图只存一张最长边 1600px 的缩略副本」）：

1. **落盘存色号字符串，不存色卡数组下标。** 若将来校准色值或重排色卡顺序，按下标存的旧工程会全部静默错位——图纸看起来正常，色号全错。存色号永远对得上。

   **⚠️ 载入时有一处必须显式重映射**：上面 `grid` 的下标是**到 `palette.codes`（本次图纸用到的色号子集）**，而引擎运行时 `Pattern.cells` 用的是**全色卡下标**（`0..palette.colors.length-1`，`EMPTY = 0xffff` 表空格）。两者在「图纸只用了部分色号」时**不同**。载入工程时必须做一次「子集 codes → 全色卡下标」的映射；只比对 `palette.id` 是**抓不到**这个错配的（同 id 但传了子集色卡），结果会是**每个色号静默标成别的名字**。计划 B 应在工程文件载入处集中做这一次重映射。

   **⚠️ 同一处还要做一次字段映射**：落盘格式写的是 `crop.w` / `crop.h` / `crop.rotate`，而运行期是 `Rect.width` / `Rect.height`（`core/image/types.ts`）**加上一个独立的** `rotation` 参数（`services/pipeline.ts`）——**字段名不同、且 `rotate` 从 `crop` 内部挪到了外面**。载入时不映射就会静默拿到 `undefined` 尺寸（进而是 NaN 网格）。
2. **原图存一份全尺寸副本，另存一张 ≤512px 的图纸缩略图当列表封面。** 原决策「只存 1600px 缩略副本」与本决策下一句自相矛盾：1600px 缩略图重跑得到的是**另一张**图纸（2000px 裁剪区的硬边细节已经没了），而 `params` 落盘的唯一意义恰恰是回到原始参数重新生成。两者解耦后，封面该是**图纸**而不是原图照片——用户在图纸库里找的是「那张小猫拼豆图」，不是「小猫照片」。代价如实体现在 UI 上：单个工程 2–6 MB，占用必须显示给用户（B1 规格 §7.3）。
3. `params` 必须落盘，否则打开旧工程无法回到原始参数重新生成。
4. **尺寸字段 `width` / `height` 显式落盘**，不从 `grid.length` 反推：反推的话 `3×4` 与 `4×3` 的图纸字节完全相同，**转置**这一类损坏无法被发现，「缓冲长度必须与宽高自洽」这条约定在这个格式上就失去了判别力。

## 5. 算法流水线

```
① 解码预览图 → ② 矩形选区 → ③ 裁剪 + 重采样到豆格
→ ④ 直方图 + median cut 压色到 N → ⑤ 代表色映射色号 → ⑥ 逐格映射
```

### ① 解码

**本流水线有两次独立的解码，尺寸不同、目的不同，不可混用：**

- **预览解码**（用于选区 UI）：位图长边不超过约 1600px，避免整图进内存。仅在选区页使用。
- **生成解码**（用于产出豆格）：宽度取 `长边豆数 × 4`，保证每格至少 4×4 像素参与面积平均。在选区确定后按选区坐标重新解码，与预览解码的分辨率无关。

原始图片的像素尺寸单独读取（只读头部即可），用于把选区 UI 上的坐标换算回原图坐标。

### ③ 裁剪 + 重采样

**关键实现点**：用 `createImageBitmap(blob, sx, sy, sw, sh, { resizeWidth })` 在**解码阶段直接裁出选区并缩放**，全图从不进内存。朴素做法（整图解码 → canvas 裁剪 → 缩放）在 4000×3000 照片上会产生约 48MB 位图，在 Android WebView 上是实打实的 OOM 风险，而用户可能只要拼一个 58×58 的小图。

目标解码宽度取 `长边豆数 × 4`，保证每格至少 4×4 像素参与平均。

**风险与降级**：`resizeWidth` 的重采样质量取决于 WebView 的 Skia 实现，若为最近邻，小图会出现噪点与摩尔纹。因此 `decode.ts` 暴露一个 **`Decoder` 接口，含两条实现**：

- 快路径：`createImageBitmap` 一次完成裁剪 + 缩放
- 保底路径：`createImageBitmap` 仅裁剪（取原生像素）→ 自行实现面积平均重采样

两条路径的输出都是 `ImageData`，下游无感。**实现第 3 步先做真机对比实验（高对比度棋盘格图）再决定默认路径，在此之前不假定快路径可用。**

### 重采样规则

- 每格 = 对应原图区域的**面积平均**（不是取中心像素；中心像素会带来明显噪点）
- 按 alpha 加权平均
- **整格全透明 → 标记为空格（`EMPTY`）**，不参与后续量化

### ④ 直方图 + median cut

- 先把像素 RGB 各压 5bit，归入 32768 个直方图桶
- 在**桶**上跑 median cut，切割轴取 Lab 空间中的最长轴，按中位数切
- 输出 N 个代表色（N = 16 / 32 / 不限）

先直方图的意义：把复杂度从"像素数"解耦为"桶数"，4 万像素与 400 万像素耗时相同。

### ⑤ 代表色 → 色号

**这是整条流水线的结构性优势**：逐格搜索需 4 万 × 221 ≈ 880 万次距离计算，而代表色只有 N ≤ 32 个，仅需 32 × 221 = **7000 次**。所以这里可以直接用最准的 **CIEDE2000**，不必为速度退让到 RGB 欧氏距离。

副作用是好的：多个代表色可能落到同一色号，实际用色比档位更少。UI 显示为「档位 32 色，实际用了 24 种」。

### ⑥ 逐格映射

每格均值色 → 最近的已选代表色 → 取其色号。预先把格子色与代表色都转成 Lab，暴力搜索即可（4 万格 × ≤32 代表色）。

### 抖动

## 6. 交互与 UI

### 6.1 流程

```
首页（图纸库）
 ├─ 新建 → 选图（相册 / 拍照）
 ├─ 系统分享进入 → 直接进选区
 └─ 打开已有工程 → 编辑器

选区页 → 设置页（长边豆数 / 色卡 / 用色档位）→ 编辑器 → 导出页
```

### 6.2 自适应布局

| 断点 | 布局 |
|---|---|
| < 768px（手机） | 单列向导，逐步推进 |
| ≥ 768px（平板） | 左右分栏：左侧大图预览，右侧参数与工具；改参数即时看到结果，无需来回翻页 |

### 6.3 平板上的三个技术点

1. **预览 Canvas 必须按 `devicePixelRatio` 缩放**（`canvas.width = cssWidth * dpr`，再 `ctx.scale(dpr, dpr)`），否则高分屏上预览发虚。导出图相反，按固定像素密度绘制，与 DPR 无关。
2. **触控命中**：一颗豆在屏幕上常只有几像素，手指点不准。编辑器默认放大到**每格 ≥ 24 CSS px**，小尺寸图自动放大铺满；支持双指捏合缩放与拖动平移；画笔支持拖动连续涂改一串格子。
3. **横屏编辑**：平板横屏 + 两栏是主要施工姿态。旋转时需重算 canvas 尺寸，工程状态不得丢失。

### 6.4 面向儿童的设计原则

不做独立「儿童模式」，整体按以下原则设计（对成人同样不减分）：

- 大触控目标、大字号
- 用词口语化：「用了几种颜色的豆子」而非「调色板量化数」
- 破坏性操作靠**可撤销**兜底，而不是弹窗拦截（弹窗小孩只会乱点）

### 6.5 编辑器

- 预览 Canvas：缩放、平移、网格线开关
- **色号调色板**：列出当前图纸用到的色号 + 每色颗数，点选即设为画笔颜色
- 工具：画笔（单颗 / 拖动连涂）、框选批量换色、吸管、撤销 / 重做
- **空格子可点**：在「空 ↔ 当前色」之间切换（抠图场景必需）
- 预览分层渲染：色块层缓存于离屏 canvas，单格改动只重绘该格；网格线 / 选中高亮画在叠加层

> **2026-10-05 更正（B4 交付时加注，上面正文不改）**：阈值 **32 px** 不变，但那句提示文案

1. 降低格子像素（下限 8px）

分片是本功能最易出 bug 的地方（坐标偏移、接缝错行、图例重复），需重点测试。

> **2026-10-05 更正（B4 交付时加注，上面正文不改）**：上面这段有**两处**被 B4 改掉，逐条说明。
> ① **降级链的顺序**（正文第 1 条）：不再是「先降格像素（下限 8px）→ 再分片」，而是

## 8. 错误处理与边界

| 场景 | 行为 |
|---|---|
| 图片解码失败（损坏文件、不支持的格式） | 明确提示具体原因，不静默失败 |
| 图片过大（长边 > 8000px） | 先只读尺寸，超阈值则提示并强制使用缩略图路径 |
| 选区过小（不足 1 颗豆） | 阻止进入下一步并提示 |
| 长边豆数越界 | 允许 1–500；超过 300 提示导出将分片 |
| 全透明图 / 生成结果全为空格 | 提示「这张图没有可拼的像素」，不产出空图纸 |
| 色卡 JSON 校验失败 | 启动即报错（内置数据不应失败，但仍校验 schema） |
| 工程文件损坏 / 版本不认识 | 提示并跳过该条，不使列表整体不可用 |
| 保存工程失败（磁盘满） | 提示，保留内存中的编辑态不丢 |
| 导出降级链全部失败 | 明确提示，并建议降低豆数 |
| 撤销栈内存上限 | 上限 50 步，超出丢弃最旧的记录 |
| 分享 / 保存相册失败 | 降级到系统分享面板 |

## 11. 色卡数据

- **主色卡：MARD 221 色**。色号体系为 `A / B / C / D / E / F / G / H / M` 九大色系 + 序号，形如 `A1`、`B3`、`H1`。这是拼豆圈的事实标准，网络流传图纸的色号基本都是这一套。
- **数据来源**：第三方公开色号表（如 [豆豆工坊 MARD 色卡](https://www.doudougongfang.com/kb/beads/mard-palette)）。抓取后整理为 `core/palette/builtin/mard221.json`。
- **已知缺口**：M 系列仅取得 M1–M4，M5–M15 需换来源补齐，补不齐则在文件中如实标注为部分数据。
- **精度声明**：MARD 官方未公开色值，第三方整理值与实物豆存在偏差。此声明必须显示在色卡 UI 与导出图纸上（「屏幕色仅供参考，以实物为准」）。
- **可替换性**：色卡为独立 JSON 文件。若品牌方对数据有异议，删除或替换该文件即可，不涉及任何代码改动。

注：未采用开源项目 `carolineyang095-code/ycs-beads-converter` 的数据，因其为 AGPL 许可，会污染本项目的 MIT 授权。`liberatrrot/BeadPalette`（MIT）可作为算法思路参考，但其色卡仅为 16 色示例子集，不复用。

### 12.1 R1 实测结论（2026-10-01）

**方法**：无头 Chrome 153 + CDP 驱动实验台 `/lab/decode`，读取页面上的「116² 首段滤波差异（回答 R1）」与「29×29 成品差异」两组 ΔRGB。ΔRGB = sRGB 三通道欧氏距离（量纲 0–441.7），只统计两侧都判为实心的格子。

**仪器可信度**：① 用同一张图在人类伙伴手动跑的 Edge 154 与上述无头 Chrome 上对比，读数**逐位一致**；② 1.00× 恒等锚点（116² 裁剪 → 116² 目标）给出**精确 0.000**，自检通过。

| 内容 | 裁剪 / 首段倍率 | 116² 首段 mean | 首段 >10 | 29×29 成品 mean | 成品 >10 |
|---|---|---|---|---|---|
| 合成棋盘格（**周期，最坏情况**） | 160²–2048² / 1.38–17.7× | 41.7–63.3 | 36–46% | 15.3–23.4 | **55–74%** |
| 随机硬边（非周期） | 512² / 4.41× | 30.2 | 35.7% | 12.4 | **48.3%** |
| 随机硬边（非周期） | 1024² / 8.83× | 34.1 | 38.1% | 13.7 | **51.2%** |
| 真实 UI 截图（抗锯齿文字） | 256² / 2.21× | 0.686 | 1.7% | 0.605 | 0.95% |
| 真实 UI 截图（抗锯齿文字） | 690² / 5.95× | 2.894 | 6.5% | 1.975 | 8.6% |
| 真实 UI 截图（抗锯齿文字） | 1280² / 11.03× | 3.367 | 9.7% | 2.022 | 4.6% |
| 真实 UI 截图（抗锯齿文字） | 160² / 1.38× | 13.703 | 18.7% | 3.677 | 15.2% |
| 恒等锚点 | 116² / 1.00× | **0.000** | 0 | **0.000** | 0 |

**结论**

1. **`resizeWidth`（`resizeQuality: "high"`）是一个真正的滤波器，确定不是最近邻**——最近邻的签名是首段 mean ≈ 126、超阈值 ≈ 61%（由与实验台同算法的仿真实测），实测全部远低于此。
2. **但它不等价于面积平均**：在**硬边内容**（线稿、粗描边、高对比图形）上，成品层**约半数豆格 ΔRGB > 10**；在**平滑/抗锯齿内容**（照片、屏幕文字）上几乎无差（成品 mean 0.6–3.7、超阈值 1–15%）。**即快路径的保真度依赖内容，且在最需要保真的硬边素材上最差。**
3. **偏差的驱动因素是内容的边缘锐度，不是降采样倍率**。受控扫描（自相似合成图案，倍率 1.38×–17.7×）下首段 mean 基本持平在 42–63；1.00× 恒等为 0。因此「大图更危险」不成立，**「硬边更危险」成立**。

**设计含义（对流水线有约束力）**

- 保底路径（`createImageBitmap` 只裁剪 + 自研面积平均）是**保真度正确**的选择——它正是规格规定的面积平均语义。
- 快路径的收益是**内存**（不把原生裁剪位图读进 JS 堆），代价是**保真度随内容退化**。
- 因此流水线**按裁剪长边择优**：裁剪边长在内存预算内（建议 ≤ 2048，即原生位图 ≤ 16MB）时走**保底路径**；超出预算时走**快路径**，并接受上述保真度 caveat。这条规则同时利用了「小裁剪内存便宜」与「大裁剪保真度风险被内存约束掩盖」两件事。
- **真机复核已做（2026-10-02，手机）：结论是滤波器跨版本稳定**，见 §12.1.1。平板（Tauri App 用的系统 WebView）仍未单独测，但已落在已测的两个版本之间。

### 12.1.1 真机复核（2026-10-02，Android 手机）

**设备**：Redmi `24122RKC7C`，**Android 16（API 36）**，安全补丁 2026-08-01。

| 组件 | 版本 | 说明 |
|---|---|---|
| 系统 WebView（`com.google.android.webview`） | **143.0.7499.192** | **Tauri App 会用这个** |
| MIUI 浏览器内置 Chromium | **135.0.7049.79** | 本次实测用的是它（该设备未装 Chrome） |

**方法**：`adb reverse` + `adb forward` 打通设备浏览器与 PC，用 CDP 脚本在设备上驱动**同一个实验台页面**、**同一张图**（2560×2697 截图 → 裁剪 1280² → 首段倍率 11.03×），读同一组数字。

**结果：与桌面 Chrome 153 逐位一致。**

| 指标 | 桌面 Chrome 153 | 设备 Chromium 135 |
|---|---|---|
| 116² 首段 max / mean / >10 | 220.05 / 3.367 / 1299 of 13456 | **220.05 / 3.367 / 1299 of 13456** |
| 29×29 成品 max / mean / >10 | 40.66 / 2.022 / 39 of 841 | **40.66 / 2.022 / 39 of 841** |
| 空格判定不一致 | 0 | 0 |

**结论与它的边界**

1. **Skia 的降采样滤波在 Chromium 135 → 153 之间逐位稳定**（同输入同输出）。目标平板的系统 WebView **143 落在这个区间内** → R1 最初的担心（「平板 WebView 可能更旧、Skia 路径不同」）**实质上被排除**。
2. **但这不是在系统 WebView 上直接测的**：本次测的是 MIUI 浏览器（自带 Chromium 135）。要在系统 WebView 上直接测需要一个宿主 App（属计划 B）。由于 135 与 153 的输出完全相同、143 被夹在中间，**不必等平板**。

**⚠️ 一次险些出错的过程留档**：控制者先用**另一张**合成的硬边图（3000²、900 块 + 200 条线）在设备上跑，得首段 mean **64.4**、成品 mean **22.5**；而桌面在**另一张**随机硬边图（1024²/2048²、300 块 + 60 条线）上是 **30–34 / 12–14** → 一度得出「**设备明显更差**」。**该结论是错的**：两次的图尺寸与密度都不同，条件不受控。改用**同一个文件**复测后，差异**完全消失**（逐位一致）。
**教训（本项目第 6 次同类）**：跨设备 / 跨版本对比**必须用同一个输入文件**，否则量到的是内容差异而不是设备差异。

### 12.1.2 保底路径的真机内存实测（2026-10-02，同一台 Android 16 手机）

**为什么测**：`MAX_EXACT_CROP_EDGE = 2048` 的**唯一依据**是那句「长边 ≤ 2048 ⇒ 原生 RGBA 位图 ≤ 16 MiB」——而它只算了 ImageData，没算 ImageBitmap 与同尺寸的 OffscreenCanvas（README 的限制条目里原先写的是「峰值约 2–3×」，但那是**推算**）。

**方法**：PC 侧生成 4096×4096 硬边测试图（随机黑块 + 随机线）→ `adb push` 到设备 → 实验台按 50% 裁剪得 **2048²**（正好压在阈值线上）→ 后台每 250 ms 采样一次 `dumpsys meminfo com.android.browser`，前台同时跑实验台。

**结果**（基线取前 15 个样本的中位数，峰值取整个窗口的最大）：

| 类别 | 基线 | 峰值 | 增量 | 与理论对比 |
|---|---|---|---|---|
| **GL mtrack（位图 / 显存）** | 22,864 KB | **42,040 KB** | **+18.7 MB** | 理论单缓冲 16,777 KB 的 **1.14×** |
| Native Heap | 72,205 KB | 77,873 KB | +5.5 MB | |
| Total PSS | 468,829 KB | 546,959 KB | +76.3 MB | **噪声过大，不作依据** |

曲线形状：`gl 22,864 → 25,176 → 42,040 → 40,816`，**峰值只持续 1–2 秒**（解码 + 重采样期间）后回落。

**结论**

1. **2048² 裁剪在真机上的图形内存增量 ≈ 19 MB**，即约 **1.14 倍**于单张 RGBA 缓冲——不是 3 倍。README 原先「峰值约 2–3×」的估算**偏保守**（保守方向安全，已按实测更新）。
2. **阈值 2048 是安全的**：真实代价约 24 MB（图形 + native），对当代设备微不足道；同一次运行里保底路径解 2048² 裁剪耗时 **213 ms**，无任何压力迹象。
3. **`Total PSS` 在浏览器进程里不能用作精细依据**（基线就约 470 MB、波动 ±80 MB）。记此，免得后来者拿它当「我们的内存占用」。
4. `pipeline.ts` 里「原生 RGBA 位图 ≤ 16 MiB」这句**本身不假**（2048²×4 恰为 16 MiB），但它**不是峰值**。原先注释按「三份全尺寸常驻」估的 32–48 MiB **偏保守**（`getImageData` 的副本并不与 `readPixels` 全程叠加）；已按本次实测改写为「约 1.5 倍、合计约 24 MB」，并注明实测出处。

### 12.2 色值权威性的实测（2026-09-30，对应 R7）

拿第二个独立公开来源（`pixel-beads.com`，可取得 A1–A26 + B1–B13 共 39 个色号）与内置色卡做**错位检验**（该检验对「两源各自测色不同」免疫：若内置数据整体错位一格，则 `A5` 会与对方的 `A6` 近乎相等）：**39 个色号中 35 个「自身位置即最近邻」**，4 个翻转的余量仅 0.3–1.7 ΔE76，而它们自身的跨源 ΔE 已在 3.2–22.9 区间 → **无系统性错位信号**。
同时实测两源的跨源 ΔE76：**中位数 7.0、最大 24.1**（A22、B8）——而 ΔE ≈ 2–3 已是人眼可辨差异。**即公开色表之间本身就不一致，「正确的 MARD 色值」并不存在。**
产品含义：色值只影响**屏幕预览相似度与最近色选择**，不影响用户能否买到豆——图纸上承载下单信息的是**色号**（MARD 色号体系是标准、可采购的标识）。故 `accuracy` 免责声明是实质为真，不是法律套话。

## 14. 实现顺序

1. **骨架**：`CLAUDE.md` / `AGENTS.md`、Tauri 2 + Vue 3 + Tailwind v4 + vitest 工程、`ci.yml`（lint + typecheck + test + `cargo check`）
2. **`core/color` + `core/palette` + MARD221 数据**（完全独立可测，不碰 UI）
3. **`core/image` 解码器对比实验**（定 R1 结论）
4. **`core/quantize` + `core/pattern`**
5. **向导页**：选图 → 选区 → 尺寸 / 档位 → 生成
6. **编辑器**：预览 + 画笔 / 框选 / 吸管 + 撤销重做
7. **导出**：施工图 / 分享图 / 分片降级 / 保存分享
8. **图纸库**：工程文件读写与列表
9. **平板自适应联调 + 真机清单**

第 2、3 步风险最低、价值最高：完全不依赖 UI，写完即可被测试证明正确，且功能二将来直接复用。

**本规格体量偏大，实现计划应拆成两份**，以第 5 步为界：

- **计划 A「引擎」**：第 1–4 步。交付物是一个被测试证明正确的纯 TS 引擎（含 R1 解码器结论）。此时还看不到界面。
- **计划 B「应用」**：第 5–9 步。交付物是能跑在平板上的完整 App。

先做 A 再做 B，好处是引擎的正确性在引入 UI 复杂度之前就已锁定——UI 阶段出现的偏差可以确定是 UI 层的问题，不必回头怀疑算法。
